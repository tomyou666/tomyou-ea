# MT4-Python 自動売買システム 設計書

本設計書は、MT4（クライアント）と Python（サーバー）で ZeroMQ を用いたリアルタイム自動売買を行うクラサバシステムの設計を定義する。生成AIが実装する際の参照とする。

- **通信・メッセージ形式の詳細**（ポート、メッセージ形式、フィールド、応答待ち・リクエストID・タイムアウト・リトライ等）は **インターフェース設計書**（`docs/インターフェース設計書.md`）を参照すること。本設計書ではアーキテクチャ・コンポーネント・データフローに重点を置く。

---

## 1. 概要・スコープ

### 1.1 目的

- MT4 と Python を **ZeroMQ のみ** で接続し、ティックデータ・注文コマンドをリアルタイムにやりとりする。
- サーバー側（Python）で**レイヤードアーキテクチャ**（presentation / application / domain / models / infrastructure）を採用し、テスト・バックテストしやすい構成とする。
- 戦略部は一括データ（CSV）とリアルタイムの両方に対応し、backtesting ライブラリでバックテスト可能とする。
- 売買結果の都度CSV記録と損益集計CSV出力を行う。

### 1.2 スコープ

| 対象 | 内容 |
|------|------|
| サーバー側 | Python / FastAPI。`server/` 配下。presentation / application / domain / models / infrastructure の各層を実装。 |
| クライアント側 | MT4 / MQL4。`client/` 配下の EA。ティック送信・コマンド受信・注文執行。 |
| 通信 | MT4–Python 間は **ZeroMQ のみ**（WebSocket は使用しない）。 |

### 1.3 用語定義

| 用語 | 定義 |
|------|------|
| ティック | ある時点の Bid/Ask/Spread 等の価格情報。MT4 から ZeroMQ で送信される。 |
| 注文 | 買い/売りの発注。Python から ZeroMQ で MT4 に送信し、MT4 が OrderSend 等で執行する。 |
| 戦略 | 加工済みデータを入力とし、シグナル（買い/売り/何もしない）を返すロジック。 |
| バックテスト | 過去データ（CSV 等）を用いて戦略の成績を評価すること。 |
| プレゼンテーション 層 | 入出力の窓口。HTTP（routers）・ZeroMQ 受信（controller）を担当。 |
| アプリケーション 層 | ユースケース・処理の制御。電文を DTO に加工する処理、トレード制御を担当。 |
| ドメイン 層 | ビジネスルール。戦略部（シグナル算出）・命令のインターフェースを配置。 |
| モデル 層 | データ構造・DTOを定義。 |
| インフラストラクチャ 層 | 永続化・外部通信の実装。売買結果・損益集計の保存（repository）、ZMQ 送信の処理を担当。 |
| 戦略部 | 加工済みデータからシグナルを算出する domain 層のコンポーネント。 |
| sender（命令部） | クライアント（MT4）へ注文・PRICE_INFO・ORDER_INFO 等の電文を加工してする。注文以外の電文も扱うためフォルダ名は **sender** とする。domain にインターフェースと実装（Mt4OrderSender 等）を配置。infrastructure は 送信処理はインフラストラクチャ層で実施する。 |

## 2. アーキテクチャ概要

### 2.1 システム構成図

```
┌─────────────────┐         ZeroMQ (PUSH/PULL)         ┌──────────────────────────────┐
│  MT4 (MQL4 EA)  │  ◄──────────────────────────────►  │  Python Server (FastAPI)      │
│                 │    ティック送信 / 注文コマンド送受信   │                              │
│  - ティック送信   │                                    │  - presentation（controller） │
│  - コマンド受信   │                                    │  - application（TradingService│
│  - OrderSend    │                                    │    ProcessService）           │
│                 │                                    │  - domain（戦略部・命令部 sender）│
│                 │                                    │  - infrastructure（payload sender）│
└─────────────────┘                                    └──────────────────────────────┘
```

- MT4–Python 間は **ZeroMQ のみ** でリアルタイムにティック送信・注文コマンド送受信を行う。

### 2.2 サーバー側レイヤー構成（レイヤードアーキテクチャ）

- **プレゼンテーション層**: controller（ZeroMQ 受信）、routers（HTTP）。受信メッセージを application に渡す。
- **アプリケーション層**: ProcessService（電文→DTO 加工）、TradingService（トレード処理の制御）。戦略部・命令部・repository の呼び出し、売買結果・損益集計保存処理の呼び出し。
- **ドメイン層**: 戦略部（TickDto を入力にシグナルを返す）。基底クラス＋子クラス。
- **モデル層**: TickDto, Signal, OrderCommand, TradeResultRow 等の DTO・データ型。
- **インフラストラクチャ層**: 命令部実装（ZeroMQ で MT4 に送信）、repository（売買結果CSV・損益集計CSV の永続化）。

### 2.3 データフロー（リアルタイム売買）

1. MT4 がティックを ZeroMQ（PUSH）で Python に送信。
2. **プレゼンテーション 層(Controller)** が ZeroMQ（PULL）で受信し、**application 層** に渡す。
3. **アプリケーション 層（ProcessService）** でティックを内部形式（TickDto）に変換。
4. **TradingService** が加工済みデータを **domain 層（戦略部）** に渡す。
5. 戦略部がシグナル（買い/売り/ホールド）を返す。
6. TradingService がシグナルに基づき **infrastructure 層（命令部）** を呼び出す。
7. 命令部が注文を JSON 化し ZeroMQ（PUSH）で MT4 に送信。
8. MT4 がコマンド受信（PULL）し OrderSend 等で執行。必要に応じて注文結果を Python に送信。

詳細は第 4 章で定義する。

## 3. 通信仕様（ZeroMQ / プロトコル）

通信の概要のみ本設計書に記載する。**ポート番号・メッセージ形式・フィールド定義・応答待ち・リクエストID・タイムアウト・リトライ**等の詳細は **インターフェース設計書** を参照すること。

### 3.1 概要

- **プロトコル**: ZeroMQ（PUSH/PULL）。MT4 → Python: 5555（ティック・注文結果等）。Python → MT4: 5556（注文・決済・PRICE_INFO・ORDER_INFO 等）。
- **設定**: ポート等は設定ファイル（`setting.ini` 等）で変更可能とする。

### 3.2 送受信の責務（実装方針）

- **Python 受信**: presentation 層の controller が非同期で PULL ソケットを listen。受信メッセージは種別（ティック CSV / order_result / price_info / order_info_list / pending_opened 等）に応じて application 層（TradingService）に渡す。lifespan でタスク起動・停止。
- **Python 送信**: 命令部が PUSH ソケットで送信。応答を待つコマンド（ORDER / CLOSE / PRICE_INFO / ORDER_INFO）では **request_id** を付与し、インターフェース設計書で定義するタイムアウト・リトライに従う。
- **MT4**: `OnTick` でティック送信（間隔制御可）、PULL でコマンド受信。応答が必要なコマンドには request_id を付けて返す。
- **再接続**: 切断時はログ出力。MT4 側は EA 再起動または再接続ロジックで対応。Python 側は lifespan 再起動でソケット再初期化。

### 4.2 アプリケーション 層：ProcessService(電文→DTO 加工)

- **役割**: 受信したティック（CSV 文字列）または一括データ（CSV 行・リスト）を、戦略部が扱う共通型（例: TickDto）に変換する。
- **基底クラス**: 抽象メソッドで「生データ → TickDto（またはリスト）」を定義。入力形式はサブクラスで異なる（1件ずつ / イテレータ）。
- **子クラス例**:
  - **TickProcessor**: ZeroMQ から受信した 1 件の CSV 文字列を TickDto に変換（リアルタイム用）。
  - **CsvBatchProcessor**: CSV ファイルを読み、1 行ずつ（またはチャンクで）TickDto に変換して yield（バックテスト用）。
- **入出力**: 第 5 章の TickDto 等を参照。ProcessService の出力は戦略部の入力と一致させる。

### 4.3 ドメイン 層：戦略部

- **役割**: 加工済みデータ（TickDto またはそのシーケンス）を受け取り、シグナル（買い/売り/ホールド）を返す。
- **基底クラス**: 抽象クラス。メソッド例: `def next(self, tick: TickDto) -> Signal` または `def next(self, tick: TickDto, context: Optional[StrategyContext]) -> Signal`。ロジックは子クラスに記載。
- **子クラス**: 具体的な指標・条件に基づくシグナルを実装。複数戦略を差し替え可能にする。
- **入力**: application 層（ProcessService）から渡される 1 件の TickDto（リアルタイムでは 1 ティックずつ。一括ではループで 1 件ずつ渡す）。
- **出力**: 第 5 章の Signal 型（Enum または Pydantic）。例: BUY / SELL / HOLD。
- **バックテスト**: 同一インターフェース（`next(tick)`）で、データソースがリアルタイムか CSV かだけ変える。backtesting ライブラリを使う場合は、そのライブラリの Strategy をラップするか、自前ループで TickDto を 1 件ずつ渡してシグナルを収集する形とする（第 6 章）。

### 4.4 アプリケーション 層：TradingService(トレード処理の制御)

- **役割**:
  - presentation 層（controller）から渡された「生ティック」を ProcessService に渡す。
  - ProcessService の出力を戦略部に渡し、シグナルを受け取る。
  - シグナルが BUY/SELL の場合、domain 層の命令部（sender）を呼び出して注文を送信する。
  - 売買結果の都度記録・損益集計の**オーケストレーション**を行う。実際のファイルへの書き込み・読み取りは **infrastructure 層の repository** に委譲する。
- **フォルダ構成**: `application/trading_service/` に配置。ProcessService と同様に**基底クラスと子クラスで分ける**。
- **基底クラス**（`base.py`）: 抽象クラス。処理フロー（受信 → 加工 → 戦略 → 命令）と、repository 呼び出しのインターフェースを定義。共通のオーケストレーションロジックはここに記載する。
- **子クラス**:
  - **TradingService**（`trading_service.py`）: 本番用。ZeroMQ 経由で届くティック・注文結果を扱い、ProcessService・戦略部・命令部・repository を利用する。
- **売買結果の都度記録**: 注文結果（order_result）またはペンディング約定（pending_opened）を受信したたびに、**infrastructure 層の trade_result_repository** に 1 行追記を依頼する（第 8 章の形式）。
- **損益集計CSV**: **infrastructure 層の repository** に、売買結果の読み取り・集計・損益集計CSV の出力を依頼する（第 8 章）。

### 4.5 domain 層：sender（命令部）と infrastructure 層：payload sender（外部送信のみ）

- **フォルダ名（domain）**: 注文以外の電文（PRICE_INFO, ORDER_INFO 等）の加工・送信も行うため **sender** とする。
- **役割（命令部・domain 層）**: 層：TradingService から渡されたシグナル（および必要なら価格・ロット等）を、MT4 が理解するコマンド（JSON）に変換して送信する。注文のほか PRICE_INFO・ORDER_INFO 等の電文も扱う。**命令部のインターフェースと実装（Mt4OrderSender, MockOrderSender）は domain/sender に残す。**
- **外部送信の分離**: **`send_payload`**に相当する処理（ZMQ ソケットへの送信）は外部とのやり取りのため、**infrastructure 層に payload sender として別途作成するのみ**。役割は「JSON ペイロードを MT4 に送信する」のみ。
- **構成**:
  - **domain/sender/**: インターフェース（base.py）と実装（mt4_order_sender.py, mock_order_sender.py）。電文の組み立て・request_id 管理・応答待ちを行う。実際の送信は infrastructure の payload sender の **send_payload** を呼ぶ。
  - **infrastructure/sender/mt4_payload_sender.py**（新規）: 外部送信のみ。ペイロード（dict）を JSON 化して ZMQ で送信する。メソッド名は **send_payload**。この処理だけをここに配置する。
- **インターフェース**: domain の **sender** にインターフェースを定義。メソッド例: `def send_order(self, order_command: OrderCommand) -> bool` 等。
- **実装クラス（domain に配置）**:
  - **Mt4OrderSender**（または Mt4Sender）: 実機用。infrastructure の payload sender（send_payload）を利用して PUSH で JSON を送信。**domain/sender** に配置。
  - **MockOrderSender**（または MockSender）: テスト用。送信内容をメモリに保持し、検証用に公開する。**domain/sender** に配置。

### 4.6 プレゼンテーション 層：controller（ZeroMQ 受信）

- **役割**: ZeroMQ PULL でティック・注文結果・価格情報・注文情報・ペンディング約定通知を受信し、種別に応じて application 層（TradingService）に渡す。lifespan でタスク起動・停止する際は、当該 controller を呼び出す。

### 4.7 インフラストラクチャ 層：repository（売買結果・損益集計の永続化）

- **役割**:
  - **売買結果の都度記録**: TradingService から渡された 1 行分のデータを、第 8 章の形式で CSV に追記する。
  - **損益集計CSV 出力**: 売買結果 CSV を読み、日別/週別/月別などで集計し、損益集計 CSV を出力する。
- **呼び出し元**: application 層の TradingService が、注文結果受信時・ペンディング約定時・集計実行時に repository を呼び出す。

## 5. データモデル・共通型定義（models 層）

本節はサーバー側 **models 層** で用いる代表的な型を記載する。**通信メッセージと Python DTO の対応**（PriceInfo, OrderInfoList, PendingOpened 等）は **インターフェース設計書** の「データ型対応表（Python DTO）」を参照すること。

### 5.1 ティック・価格データ

- **TickDto**（Pydantic または dataclass）
  - symbol: str
  - bid: float
  - ask: float
  - spread: int
  - time: datetime または str（パース済み）

- 必要に応じて **OHLCV**（open, high, low, close, volume, time）を定義し、加工部でティックから集約する場合は使用する。

### 5.2 シグナル

- **Signal**（Enum）
  - BUY
  - SELL
  - HOLD

- 注文量などを含める場合は **SignalResult** のような Pydantic モデルで `signal: Signal`, `lots: float`, `sl: float`, `tp: float` 等を定義する。

### 5.3 注文・約定・応答

- **OrderCommand**（Pydantic）
  命令部が MT4 に送るコマンド。インターフェース設計書に合わせ、応答を待つコマンドでは **request_id** を必須とする。
  - action: Literal["ORDER", "CLOSE", "PRICE_INFO", "ORDER_INFO", ...]
  - request_id: str（ORDER / CLOSE / PRICE_INFO / ORDER_INFO では必須）
  - symbol, type（BUY / SELL / BUY_LIMIT / SELL_LIMIT / BUY_STOP / SELL_STOP）, lots, price, sl, tp, ticket 等

- **OrderResult**（MT4 から返ってくる注文結果のモデル）
  - type: Literal["order_result"]
  - request_id: str（送信したリクエストの request_id と一致することを検証する）
  - ticket: int
  - status: str（SUCCESS, FAILED:&lt;コード&gt;, CLOSED, CLOSE_FAILED 等）

- **PriceInfo**, **OrderInfoList**, **PendingOpened** 等の形式はインターフェース設計書を参照。

### 5.4 売買結果CSV・損益集計CSV のカラム

- 売買結果CSV（都度記録）: 第 8 章で定義。
  - 想定カラム: 日時, シンボル, 方向, 数量, 約定価格, 損益, チケット, 備考 等
- 損益集計CSV: 第 8 章で定義。
  - 想定カラム: 集計単位（日/週/月）, 開始日, 終了日, 約定回数, 損益合計 等

これらは第 8 章のファイル仕様と整合させる。

## 6. 戦略部のバックテスト・一括データ対応

### 6.1 方針

- 戦略は「1 件ずつデータを受け取る」インターフェースに統一する。
  - 例: `strategy.next(tick: TickDto) -> Signal`
- データソースが「リアルタイム」か「一括CSV」かは、**呼び出し元（TradingService またはバックテストループ）** が変える。戦略側は同じ `next(tick)` のみを実装する。

### 6.2 リアルタイム

- ZeroMQ でティックが届くたびに、presentation 層の controller が受信し、TradingService に渡す。ProcessService で 1 件 TickDto に変換し、TradingService が戦略の `next(tick)` を呼ぶ。

### 6.3 一括データ（CSV）

- CSV を application 層の ProcessService（CsvBatchProcessor 等）で 1 行ずつ TickDto に変換し、ループで `strategy.next(tick)` を呼ぶ。
- バックテスト時は、そのループ内でシグナルに応じた約定シミュレーション・損益計算を行う（backtesting ライブラリを利用する場合は、そのライブラリのデータ形式に合わせて TickDto または OHLCV を渡す）。

### 6.4 backtesting ライブラリの利用

- 既存の `pyproject.toml` の dev 依存に `backtesting` があることを前提とする。
- 方針の例:
  - 自前で「CSV → TickDto のイテレータ → strategy.next を逐次呼び出し」でバックテストする。
  - または、backtesting ライブラリの `Strategy` をラップし、内部で本プロジェクトの戦略クラス（基底クラスの子クラス）を呼ぶ形にする。
- いずれにせよ、戦略のロジックは 1 箇所（子クラス）にのみ書き、リアルタイムとバックテストで共有する。

## 7. 依存性注入（DI）・設定

### 7.1 方針

- 既存の `config/di.py`（injector 利用）を拡張する。
- 各層のコンポーネントは **インターフェース（抽象基底クラス）** にバインドし、本番用/テスト用の実装を切り替える。

### 7.2 バインド例（レイヤードアーキテクチャ）

- **ProcessService**（application 層）: 本番では TickProcessor、テストでは MockProcessor または CsvBatchProcessor。
- **Strategy**（domain 層）: 本番では具象戦略クラス、テストでは固定シグナルを返すモック。
- **TradingService**（application 層）: 本番では TradingService（基底クラスの子クラス）。
- **Sender**（命令部のインターフェース・実装。domain/sender）: 本番では Mt4OrderSender、テストでは MockOrderSender。いずれも domain に配置。実際の ZMQ 送信は infrastructure の payload sender の **send_payload** に委譲する。
- **TradeResultRepository**（infrastructure 層）: 売買結果・損益集計の永続化。本番用実装をバインドする。

### 7.3 設定ファイル

- **setting.ini**（または .env）で以下を管理する想定とする。
  - ZeroMQ 受信ポート・送信ポート
  - 売買結果CSV・損益集計CSV の出力ディレクトリ
  - ログレベル
- 既存の `resources/setting.ini` を拡張する。共通読み込みは `share/fileIo_util` や `share/const` を参考にする。

## 8. 売買結果・損益のCSV出力仕様

### 8.1 売買結果CSV（都度記録）

- **目的**: 約定（または注文送信）が行われるたびに 1 行追記する。
- **ファイル名**: 例 `trade_results_YYYYMMDD.csv`（日単位で 1 ファイル）または `trade_results.csv`（1 ファイルに追記）。設定で切り替え可能とする。
- **エンコーディング**: UTF-8。BOM の有無は設定で統一。
- **カラム例**:

| カラム名 | 説明 | 例 |
|----------|------|-----|
| executed_at | 約定日時（サーバー時刻またはMT4時刻） | 2025-01-29 12:00:00 |
| symbol | 通貨ペア | USDJPY |
| side | 買い/売り | BUY / SELL |
| lots | ロット数 | 0.01 |
| price | 約定価格 | 149.123 |
| ticket | MT4 チケット番号 | 12345678 |
| status | 結果 | SUCCESS / FAILED |
| pnl | 損益（決済時のみ。建玉時は空または0） | 100.5 |
| memo | 備考 | （任意） |

- **追記方式**: 開くたびに追記（append）。**infrastructure 層の repository** が 1 約定ごとに 1 行書き込む。TradingService が repository を呼び出す。

### 8.2 損益集計CSV

- **目的**: 売買結果CSV を元に、期間別の損益を集計して出力する。
- **ファイル名**: 例 `pnl_summary_YYYYMMDD_HHMMSS.csv` または `pnl_summary.csv`（上書きまたは追記は仕様で決定）。
- **カラム例**:

| カラム名 | 説明 | 例 |
|----------|------|-----|
| period_type | 集計単位 | daily / weekly / monthly |
| period_start | 期間開始日 | 2025-01-29 |
| period_end | 期間終了日 | 2025-01-29 |
| trade_count | 約定回数 | 10 |
| total_pnl | 損益合計 | 500.25 |
| win_count | 勝ち回数 | 6 |
| loss_count | 負け回数 | 4 |

- **出力タイミング**: **TradingService** から明示的に「集計して出力」を呼ぶ。TradingService は **infrastructure 層の repository** に集計・出力を依頼する。例: 日次バッチ、または API エンドポイントから手動実行。

## 9. エラーハンドリング・ログ・再接続

### 9.1 ZeroMQ の切断・再接続

- **Python**: 受信ループ内で `zmq.ZMQError` をキャッチし、ログ出力後に短い sleep して再試行する。lifespan 終了時にタスクを cancel し、ソケットを close・context.term する。
- **MT4**: EA 初期化で connect、OnDeinit で disconnect。接続失敗時はログを出し、必要なら再接続フラグで OnTick 内で再接続を試みる。

### 9.2 例外の扱い

- **ProcessService**: パース失敗時は例外を投げるか、None を返して TradingService でスキップする。いずれもログに記録する。
- **戦略部**: 例外は TradingService でキャッチし、ログを出してそのティックはスキップ（シグナル HOLD 扱い）する。
- **命令部**: 送信失敗時は False を返し、TradingService でログとリトライ方針を決める。
- 既存の `app_server/app/exception_handler.py` は HTTP 用のため、ZeroMQ 受信タスク内の例外はタスク内で try/except する。

### 9.3 ログ

- 既存の `share/logger_util.py` の `get_logger()` を使用する。
- ティック受信・注文送信・戦略シグナル・CSV 記録・集計結果など、重要イベントは INFO で記録する。パースエラー・送信失敗は WARNING または ERROR。
- ログレベルは設定ファイルで変更可能とする。

## 10. デプロイ・起動順序・環境

### 10.1 Python サーバー

- **実行**: `uv run fastapi dev app_server/main.py --port 8000`（または `uvicorn`）。作業ディレクトリは `server/`。
- **依存**: `server/pyproject.toml` の dependencies に fastapi, pyzmq, pydantic 等が含まれる。dev に backtesting, pytest 等。
- **環境変数**: 既存の `IS_DEBUG` 等。ZeroMQ ポートや CSV 出力先は setting.ini から読み込む想定。

### 10.2 MT4

- EA をチャートにアタッチ。入力で ServerAddress（例 `tcp://localhost`）、PushPort（5555）、PullPort（5556）を指定。
- libzmq.dll / mql-zmq 等は MT4 の Libraries に配置する。

### 10.3 起動順序

1. 先に Python サーバーを起動し、PULL/PUSH の bind を待つ。
2. MT4 で EA を有効にし、connect する。
3. ティックが流れ始めたら、戦略・命令が動作することを確認する。
